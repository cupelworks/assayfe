Four concepts, each built on the one before it. Everything else in the app is a view onto these.

Dataset

A named collection of prompt / expected-output / model-output rows, usually imported from a .jsonl file. Source material for bulk test creation - never run directly.

Test

A live, always-editable input, an optional expected output, an optional recorded model output, and a set of assigned test types. Leave the model output empty and a run asks the application under test for its answer instead. Can be run on its own at any time.

Test set

A named collection of frozen test snapshots ("entries"). Adding a test copies its current state in - the set never re-syncs with the live test afterward.

Test plan

A named campaign made of test sets. Running a plan fans out over every entry in every set currently linked to it.

The evaluation strategies a test is scored with - assigned per test, not fixed. A test with none assigned can't be run.

Each type belongs to a category, and some require a reference - an expected_output to compare against - and can't score a test that doesn't have one. Others take their own configuration instead, or as well: a numeric threshold the score is checked against, or a custom rubric for an LLM-as-judge type to grade against. A test can't be saved until every assigned type's required setup - reference or otherwise - is actually filled in. Inactive types stay visible for history but can no longer be newly assigned.

The catalogue

The current list of categories, costs, limitations, scoring engines and what each one is best for - each type's card shows which engine scores it, its settings, and, for a threshold-scored type, its range and when the score meets it.

The one rule the whole app is built around: once a run exists against something, that something stops changing. This is what makes a past run's record trustworthy months later.

The building blocks above, combined into the three flows you'll actually use.

Workflow 1

Quick check on a single test

You're authoring or tweaking a test and want to see how it scores right now, with no ceremony.

Reads the test at the instant it runs and keeps its own record of it from that moment - editing the test again afterward doesn't touch that run's history, though the next run you create will use the updated content. There's no live/replay pair here: with no set or plan membership, there's nothing for those terms to distinguish.

Workflow 2

Reproducible testing through a test set

You want a stable, comparable baseline - a fixed group of tests you can re-run over and over, on demand or after a change, and trust that "the same test" means the same input every time.

The dataset step is optional - a test can be written by hand instead. What matters is the moment it's added to the set: its content is copied into a frozen-eligible entry, independent from the live test from then on. Live re-runs whatever entries are in the set today. Replay re-runs the exact same entries a past execution used, with their content exactly as it was back then. Nothing that happens afterward can change what a replay sees.

Workflow 3

Running a campaign across several sets

You want to execute multiple test sets together as one unit - a release check, say, that spans several baselines at once - and track them as a single campaign over time.

One level up from workflow 2, same live/replay shape. A plan can link any number of test sets, and one run fans out over every entry in every set currently linked - live uses today's links, replay reuses exactly what a past plan execution touched. The links themselves never freeze, so you can add or remove sets from the plan at any time, even after it's been run.

A plan's connection to a test set is a pointer, not a snapshot - and that pointer never freezes.

You can link or unlink test sets to a plan at any time, even after the plan has been run - this is the one relationship in the app that's exempt from the freeze rule above. What still freezes, exactly as before, is the content each linked set's entries ran against. So re-linking or unlinking sets never rewrites history: a past plan execution stays anchored to whichever entries it actually used, no matter how the plan's membership changes afterward.

Nothing is lost

Unlinking a test set from a plan - or an entry from a set - never deletes anything or breaks a past run's record. It only changes what a future live run will fan out over.

Every run moves through the same two lifecycle states, then lands on one of four outcomes - a summary of how each check did in that run, not just "did it finish." An outcome is what happened once: a GenAI application can answer differently each time, so one run is a signal, not a verdict - repeat the run before concluding that something passes or fails.

While it runs Created, not yet picked up. Currently executing.
How it ended Every check was met in this run. Some checks were met in this run, some weren't. No check was met in this run. The run couldn't be evaluated at all - something went wrong before any test type could be checked (the model couldn't be reached, the application under test kept failing, or the test's content couldn't be loaded). Unlike Red, no check was missed here - nothing was checked.

What was actually scored. Every finished run records the exact answer its checks judged - the evaluated output. If the test had a recorded model output, that's what was scored. If it had none, the run asked the application under test and scored its live reply - which is why two runs of the same test can legitimately differ. The run's detail page shows the evaluated output and labels which of the two it was.

One check that can't evaluate doesn't sink the run. If a single check can't run - no judge chosen for a judge check, say, or a judge that timed out - the run's page shows it as "couldn't run", with the reason, and the rest still run. In the run's outcome it counts as not met, so the run usually lands on Amber, not Not Ran. Not Ran is reserved for nothing being checkable at all.

One run is a signal; a verdict needs many. "Run with statistics" on a test, a test set or a test plan runs it many times as one batch, then a statistical test decides each check, 95% sure unless you choose otherwise. Each time is a full run, paid for like any other - the page shows how many runs, application calls and judge calls before anything is created, and what each verdict will take at that size.

A batch, while it runs Created, no run started yet. Runs going. No verdicts until every run has finished. Stopped before every run ran. What ran is kept. A trial finished: it shows how each check behaves, and gives no verdict.
Its verdict Every check reaches the target. At least one check falls short. Every run finished, but there weren't enough runs to tell either way. A new, larger batch would likely settle it - the result says about how large, or that it would take more than a batch can run. No check could be decided: every run Not Ran, or every check errored.

What a verdict says. "It passes at least 9 times in 10 (95% sure)": the runs leave a range the real pass rate can be in. The check is Passed when the whole range is above the target, Failed when it's below, Inconclusive when the target is inside it. A run stays Green, Amber or Red; only a batch is Passed or Failed.

Did my change help? Run a batch before the change and one after, then "Compare with…" on the second: check by check, B is better, worse, or shows no clear difference at this size.

Short answers to the "why won't it let me do that?" moments.

09.1

Why did renaming to the same name just work, instead of failing?

Resubmitting a dataset's, test set's, or test plan's own current name is always treated as success - the uniqueness check only runs when the name actually changes.

09.2

Why won't this test save?

Every test type you assign has to have its own required setup actually filled in before you can save - a reference (expected output) for types that compare against one, or that type's own config otherwise (a numeric threshold, a rubric). Assigning a type doesn't waive what it needs to run.

09.3

Why did two runs of the same test get different answers?

The test has no recorded model output, so each run asks the application under test live and scores whatever it answers that time. Record a model output on the test if you want every run to judge the same fixed answer.

09.4

Every run passed - why is the batch Inconclusive?

Too few runs to be sure. With a 90% target, 95% sure, it takes 29 passes out of 29: a check that passes only 9 times in 10 would still pass 28 in a row more than 1 time in 20. The page shows the minimum before you start, and offers one spare time in case a run is Not Ran.

09.5

One check shows an error message, but the run isn't Not Ran - why?

A check that can't evaluate - a regex that won't compile, a bad threshold - counts as not met on its own, with the reason as its detail, and the other checks still run. Not Ran only means nothing could be checked at all: the model or the application under test was unreachable, or the content couldn't be loaded.

09.6

Why can't I delete this test?

A test is blocked while it's still snapshotted into any test set, or has any run - standalone or otherwise - against it. Unlink or clean those up first.

09.7

Why can't I edit this entry anymore?

Once any run references a test set entry, it freezes for good. You can still unlink it from the set (content and run history stay intact) or delete it outright if it's never been run.

09.8

Why won't this test set or test plan delete?

A test set is blocked while any of its entries has ever been run. A test plan is blocked once it has ever been executed at all - full stop, no "force delete." A plan's links to its test sets are the one exception: those can always be added or removed.

09.9

I deleted a dataset (or some rows) I'd already used to create tests - did that break those tests?

No. A test owns a full copy of its own data from the moment it's created; deleting the source dataset or rows only clears a traceability pointer, never the test's content.

09.10

I selected several rows and the bulk action failed - why did nothing happen at all?

Every bulk action (delete, unlink, add, link) is all-or-nothing. If any single selected item fails a guard, the whole batch is rejected - there's no partial success.

09.11

Where do I point Assay at the application it should test?

The Settings page (at the right of the header) is where you set the application under test - URL, method, headers, request body, answer path, timeout and retries. Use "Test connection" to try your changes before saving them; a saved change applies from the next run.
