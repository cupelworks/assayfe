Guide

How Assay works

The mental model behind datasets, tests, test sets, test plans and runs - and why the app behaves the way it does.

The building blocks

Four concepts, each built on the one before it. Everything else in the app is a view onto these.

Dataset

A named collection of prompt / expected-output / model-output rows, usually imported from a .jsonl file. Source material for bulk test creation - never run directly.

Test

A live, always-editable input with an optional expected/actual output and a set of assigned test types. Can be run on its own at any time.

Test set

A named collection of frozen test snapshots ("entries"). Adding a test copies its current state in - the set never re-syncs with the live test afterward.

Test plan

A named campaign made of test sets. Running a plan fans out over every entry in every set currently linked to it.

Test types

The evaluation strategies a test is scored with - assigned per test, not fixed. A test with none assigned can't be run.

Each type belongs to a category, and some require a reference - an expected_output to compare against - and can't score a test that doesn't have one. Others take their own configuration instead, or as well: a numeric threshold the score has to clear, or a custom rubric for an LLM-as-judge type to grade against. A test can't be saved until every assigned type's required setup - reference or otherwise - is actually filled in. Inactive types stay visible for history but can no longer be newly assigned.

See the full test types catalogue for the current list of categories, costs, limitations and what each one is best for.

From editable to frozen

The one rule the whole app is built around: once a run exists against something, that something stops changing. This is what makes a past run's record trustworthy months later.

1
Test created
Freely editable, forever - even after it has standalone runs against it.
2
Added to a test set
Its current input, expected output and test types are copied into a new entry. The live test and the entry are now independent.
3
Entry still editable
You can fix a typo or adjust test types on the entry itself, same as any live test - until step 4.
4
First run created
The moment any run references the entry - even while still Pending - it freezes. No unfreeze path, ever.
A frozen entry can still be unlinked from its set (it keeps its content and run history, it just leaves the set's membership) or deleted along with the whole set - but its content itself never changes again.

Standalone, live, and replay

Every run is created one of these three ways. That choice decides what the run reads, and whether it can be replayed later.

Standalone

Run a test directly

Runs the test as it is right now. The run keeps a record of exactly what it checked, so if you edit the test later, this run's history stays as it was. A direct run always stands on its own; it isn't part of a test set or plan.

LiveReplay

Run a test set

Live fans out over whichever entries are in the set right now. Replay re-runs the exact same entries a past execution used, with their content exactly as it was back then - even if the set's membership has changed since, or the live tests they came from have since been edited.

LiveReplay

Run a test plan

Same live/replay shape, one level up: fans out across every entry in every test set currently linked to the plan (live), or the exact entries a past plan execution used (replay).

Putting it into practice

The building blocks above, combined into the three flows you'll actually use.

Workflow 1

Quick check on a single test

You're authoring or tweaking a test and want to see how it scores right now, with no ceremony. Each run keeps its own record of what it checked, so it won't drift if you edit the test afterward - there's just no set or plan here to compare a "live" run against a "replay" of one.

Test
→run standalone
Run

Reads the test at the instant it runs and keeps its own record of it from that moment - editing the test again afterward doesn't touch that run's history, though the next run you create will use the updated content. There's no live/replay pair here, though: with no set or plan membership, there's nothing for those terms to distinguish.

Workflow 2

Reproducible testing through a test set

You want a stable, comparable baseline - a fixed group of tests you can re-run over and over, on demand or after a change, and trust that "the same test" means the same input every time.

Dataset
→import rows
Test
→add to set
Test set entry
→run live / replay
Run

The dataset step is optional - a test can be written by hand instead. What matters is the moment it's added to the set: its content is copied into a frozen-eligible entry, independent from the live test from then on. Live re-runs whatever entries are in the set today. Replay re-runs the exact same entries a past execution used, with their content exactly as it was back then - even if you've since edited the live test, or the set's membership has changed. Nothing that happens afterward can change what a replay sees.

Workflow 3

Running a campaign across several sets

You want to execute multiple test sets together as one unit - a release check, say, that spans several baselines at once - and track them as a single campaign over time.

Test set
→link to plan
Test plan
→run live / replay
Run  × every entry, every linked set

One level up from workflow 2, same live/replay shape. A plan can link any number of test sets, and one run fans out over every entry in every set currently linked - live uses today's links, replay reuses exactly what a past plan execution touched. The links themselves never freeze, so you can add or remove sets from the plan at any time, even after it's been run.

Test plans link, they don't own

A plan's connection to a test set is a pointer, not a snapshot - and that pointer never freezes.

You can link or unlink test sets to a plan at any time, even after the plan has been run - this is the one relationship in the app that's exempt from the freeze rule above. What still freezes, exactly as before, is the content each linked set's entries ran against. So re-linking or unlinking sets never rewrites history: a past plan execution stays anchored to whichever entries it actually used, no matter how the plan's membership changes afterward.

Unlinking a test set from a plan - or an entry from a set - never deletes anything or breaks a past run's record. It only changes what a future live run will fan out over.

Run lifecycle & statuses

Every run moves through the same two lifecycle states, then lands on one of four outcomes - a summary of how each assigned test type did, not just "did it finish."

Pending
Created, not yet picked up.
Running
Currently executing.
Green
Every assigned test type passed.
Amber
Some assigned test types passed, some didn't.
Red
Every assigned test type was checked, and none passed.
Not Ran
The run couldn't be evaluated at all - something went wrong before any test type could be checked (e.g. the model couldn't be reached, or the test's content couldn't be loaded). Unlike Red, nothing here failed a check - nothing was checked.

Guardrails you'll bump into

Short answers to the "why won't it let me do that?" moments.

?
Why did renaming to the same name just work, instead of failing? Resubmitting a dataset's, test set's, or test plan's own current name is always treated as success - the uniqueness check only runs when the name actually changes.
?
Why won't this test save? Every test type you assign has to have its own required setup actually filled in before you can save - a reference (expected output) for types that compare against one, or that type's own config otherwise (a numeric threshold, a rubric). Assigning a type doesn't waive what it needs to run.
?
Why can't I delete this test? A test is blocked while it's still snapshotted into any test set, or has any run - standalone or otherwise - against it. Unlink or clean those up first.
?
Why can't I edit this entry anymore? Once any run references a test set entry, it freezes for good. You can still unlink it from the set (content and run history stay intact) or delete it outright if it's never been run.
?
Why won't this test set or test plan delete? A test set is blocked while any of its entries has ever been run. A test plan is blocked once it has ever been executed at all - full stop, no "force delete." A plan's links to its test sets are the one exception: those can always be added or removed.
?
I deleted a dataset (or some rows) I'd already used to create tests - did that break those tests? No. A test owns a full copy of its own data from the moment it's created; deleting the source dataset or rows only clears a traceability pointer, never the test's content.
?
I selected several rows and the bulk action failed - why did nothing happen at all? Every bulk action (delete, unlink, add, link) is all-or-nothing. If any single selected item fails a guard, the whole batch is rejected - there's no partial success.
