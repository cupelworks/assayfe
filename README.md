# Assay FE

Angular 22 front-end for the Assay evaluation API (v0.10.0). Modernist design system (Archivo, red/ink on light ground, zero radius, 2px rules); dark mode via `[data-theme="dark"]`.

## Run

```
npm install
npm start          # http://localhost:4200
```

Backend must allow CORS from `http://localhost:4200`. API base is set in `src/app/app.config.ts` (`ASSAY_API_BASE`).

## Screens → endpoints

- **Overview** - counts, recent test-set/test-plan executions, and a "Run status" box (`GET /runs`, 500 newest, every origin) whose six tiles (Pending/Running/Green/Amber/Red/Not Ran) each link to the filtered **Runs** list below. New test.
- **Runs** (`/runs`) - every run in the system (`GET /runs`), optionally filtered server-side by `?status=`/`?origin=` (set from the Overview tiles or the on-page origin chips). Per-row name resolved with one lookup call each (`GET /tests/{id}` for Standalone, `GET …/test-runs/{run}` for Test set/Test plan). Created column sorts client-side (arrow toggle) over whatever page is loaded. Run id is click-to-copy.
- **Datasets** - list (name-filterable, Created sortable); _Import from JSONL_ (`POST /datasets/path`). **Dataset detail** - paged rows (`GET /datasets/{id}/rows`), edit row (`PATCH /datasets/rows`), add rows / replace all rows (paste JSONL → `POST`/`PUT /datasets/rows`), delete selected rows (`DELETE /datasets/rows`), rename (`PATCH /datasets/name`), delete (`DELETE /datasets`), _Create tests from rows_ (`POST /tests/from-dataset`).
- **Tests** - list, filter, bulk delete (`DELETE /tests`), New test (`POST /tests`). **Test detail** - edit (`PATCH /tests/{id}`), clear the recorded model output (a "Clear" button beside it, confirm dialog, sends only `model_output: null` - runs then ask the application under test), delete, _Run standalone_ (`POST /runs/standalone/{id}`), standalone runs list (status + click-to-copy run id, independent of the row's own link) → **Standalone run detail** (`GET /runs/standalone/{id}/test-runs[/{run}]`).
- **Test sets** - list (with an Entries column, free from `entry_count` on `GET /test-sets`), New (`POST /test-sets`). **Test set detail** - entries (`GET …/entries`, each tagged "frozen" once it has a run against it), _Add tests_ (`POST …/entries` `[{id}]`), _Unlink_ (`PATCH …/entries`), _Delete entries_ (`DELETE …/entries`), edit frozen entry (`PATCH …/entries/{entry}`), rename, delete, _Run live_ (`POST /runs/test-sets/{id}`), executions (per-row status breakdown, click-to-copy id, "replayed" reference linked, polls while anything shown is Pending/Running) + _Replay_ (`POST /runs/test-sets/{id}/executions/{exec}`).
- **Test plans** - list (Linked sets column, free from `linked_set_count` on `GET /test-plans`), New. **Test plan detail** - linked sets (`GET …/entries`, each row's Entries count free from the embedded `test_set.entry_count`), _Link_ (`POST …/entries`), _Remove_ (`DELETE …/entries`), rename, delete, Run live / Replay under `/runs/test-plans/…`.
- **Execution** - status counts (current page only) + run list (`GET …/executions/{exec}/test-runs`) with a per-row Results bar (pass/fail share + "x/y", from the same per-row `test-runs/{run}` call already made for the name), Created and Executed columns both independently sortable (arrow toggle, unfinished runs sort last), click-to-copy Entry/Run ids, Replay, polls while any loaded row is Pending/Running. **Run detail** - status, evaluated output (the exact answer the checks judged, badged "Recorded" or "From application" per `output_source`; "(empty answer)" when the application answered with nothing, pretty-printed when it answered with JSON, and for an application answer a note that it was read at the Answer path in Settings), per-type results (score on the type's own scale, bar scaled to that range - BLEU 0–100, cosine −1..1; a score-less result shows pass/fail only) with the config actually checked against (e.g. "Minimum score to pass: 0.75"; a judge shows the rubric it graded with, from the result's own `rubric` stamp - "Rubric: …" for its own, "Default rubric: …" otherwise - and "Judged by: <model>" from its `judge` stamp; long values clamp behind a More/Less toggle) and two lines naming what scored it - *Engine* (e.g. `regex`) and *Engine settings* (e.g. `mode: search, timeout_seconds: 1`, omitted when there are none) - frozen entry snapshot (`GET …/test-runs/{run}`), link to originating test, polls while the run itself is Pending/Running.
- **Test types** - catalogue from `GET /tests/types?test_category=…` (all three categories fetched in parallel), cached by `TestTypesStore` for reuse in the test forms and in run detail's config labels. Category tiles show an active-only count and a one-line blurb; click one to narrow the list to just that category, click again to clear. A legend tile explains the `fast` / `needs setup` / `inactive` tags. Below that: text filter (name, description, best for, engine), show-inactive toggle, a page-scoped Refresh (force-reloads the type catalogue past its normal load-once cache), and cards (description, best for, limitations, cost, needs-setup) that expand on click for category, the *Engine* and *Engine settings* that score it (two rows, mirroring the API's `engine` / `engine_settings`; the settings row is omitted when there are none), a judge's default rubric, every configuration field - with a numeric field's native range and pass rule ("0 to 100, passes when score ≥ threshold") - and added date.
- **Guide** - static "How Assay works" explainer: the core dataset/test/test-set/test-plan model (incl. what a run does when a test has no recorded model output), what a result looks like per test-type category, the freeze-on-execution rule, standalone vs. live vs. replay runs, three concrete end-to-end workflows, test-plan linking, run statuses plus evaluated output and why one failing check isn't Not Ran, and a guardrail FAQ. No API calls.
- **Settings** (`/settings`, the gear beside the theme toggle) - what Assay tests and how it's set up, in the backend's own grouping, laid out like Overview: a statement headline, a strip of four summary tiles (application URL, judge provider and model, workers' verdict, operations - each jumps to its section), then each group on Overview's 2/3 | 1/3 grid - the form on the left (ruled field blocks, label on top, fields paired two per row), Test connection on the right. *Application under test* is editable (`GET`/`PATCH`/`DELETE /settings/target`): target URL, method, headers, request body, answer path, timeout, retries - each field naming the `ASSAY_TARGET_*` env var it falls back to, with a plain-language hint; a tag says whether the values come from the server's environment or were saved in Assay. Save and Discard sit top-right of the form with an "N unsaved changes" count; Save sends only the changed fields, Discard reverts, "Reset to environment values" (confirm dialog) drops what was saved, and the API's 422s show under the matching field. *Test connection* sends one request with the form as it is - unsaved changes included, never saved - via `POST /settings/target/checks`, polls the check every second and shows the result as status tiles (a run-status dot with Answered/Failed, the HTTP status, the latency) plus the answer or the error, giving up with "No worker answered" after the checked timeout + 30 s. *LLM judge* (`/settings/judge`) is the same kind of form - provider (None / Anthropic / OpenAI), model, URL (endpoint) - optional: the whole endpoint, called exactly as written, empty for the provider's own - API key variable, timeout, retries, each falling back to an `ASSAY_JUDGE_*` variable, with examples that follow the chosen provider. The key itself never passes through the UI or the API: the section says which variable the worker reads it from ("API key: read from ANTHROPIC_API_KEY on the worker (its environment or .env)") or "No judge configured", and its Test connection (no input - the judge gets a fixed question) is how you find out whether the key is set on the worker. Both groups are one shared component. *Workers* (`GET /health/worker`, checked when the page opens and on "Check again") shows the broker (reachable or not, with its error), how many workers are connected and how many need a restart, a row per worker (name, version, Up to date / Restart needed, and the API's problem sentence as sent), and the verdict for its `status` - Ready, Restart needed, No workers, Broker unreachable - with what to do; the strip gets a fourth tile for it. *Operations* is read-only; connection strings are shown only as "Configured".

## Testing
There's no automated FE suite; `docs/testing_checklist.md` is the manual, screen-by-screen UI checklist to run against a live API + worker.

## Structure

`api/` models + one-method-per-endpoint service (incl. `SettingsApiService`) + root `CatalogStore` + `TestTypesStore` (with the pure display helpers `numericFieldHint` / `engineSettingsLabel` / `defaultRubric` shared by the catalogue, the config inputs and run detail - `defaultRubric` by the catalogue only) · `shared/` formatters (incl. `errText`, and `fieldErrors` to split an API error into per-field messages and the rest), page.css, `Paged`/`PagerComponent`, `ActionRunner`, `DateSort`, `TextFilter`, `Selection`, `FieldErrorStore`, `assayNumber` + `parseDecimal`, `pollWhile`, `<assay-rel-time>`, `<assay-copy-button>`, `<assay-chevron>`, dialogs (generic, name, confirm, pick, test form), test-type-picker · one folder per area (`datasets`, `tests`, `scopes`, `runs`, `test-types`, `guide`, `settings`) · `shell/` header/footer/theme.

## Notes

- Checks: lists show what a test checks as one tag per type, with a count when it repeats ("Contains ×2"); the form and a run's results, which give each check its own row, show check names. A test holds a list of checks - each a catalogue test type with its own name, settings and answer path - and a type can appear more than once (two Contains, two JSON Field Equals on different paths). Every form (new/edit test, edit entry, create tests from dataset) edits them in one table, `shared/checks-table.component` - Type | Name | Settings | Remove, checks of a type grouped with "+ Add another <type>" under them, and "+ Add a test type" opening the catalogue in place (search, "Hide types needing setup", the categories with their counts beside a fixed-height scrolling list of types with description, cost and "needs setup" tags, and Add). Name is optional: empty shows the name the API will give (the type's name, numbered past every name in use - "Contains", "Contains 2"); a name used twice, ignoring case, blocks saving. Editing sends every name back as it came, so a check keeps its identity and its results stay comparable across runs.
- Settings are rendered from each type's `config_fields`, by `kind`, never by type name: a box that grows with its text - or with its example, so an empty rubric shows the whole default - for `multiline`/`rubric` and, in monospace without spell-check, `json`/`json_schema`/`regex`; a single-line monospace input for `jsonpath`; a number input for `numeric` (digits-only for an `integer` field). Each shows the API's `placeholder` and `hint`; a type with no settings says so. Saving is blocked, with the reason, while a required field is empty, a number is out of range or not whole, JSON doesn't parse or a JSONPath doesn't start with `$` (`checkIssues` in `api/checks.ts`); the API repeats its own checks on save (a regex is left to it - it uses Python's syntax).
- Per-check answer path: each check has a collapsed "Advanced" with an optional "Read from (JSONPath)" (`answer_path`) - which part of the application's reply it reads instead of the default answer. Opened automatically when a path is set, and a "reads $.stop_reason" mark under the check's name shows it. Forms always send each check's `answer_path` back (`toAssignments`), because the API replaces the list on save and reads a missing key as the default. Run detail shows "read from $.x" under a check that used its own path, and the application's whole reply in a collapsed, pretty-printed "Full application reply".
- Test form (new/edit test, edit entry): the Expected output label says live whether it's needed - "required by BLEU, Exact Match (whitespace-sensitive)" for every check's type that needs a reference, "optional" when none does - and Save stays blocked while a required one is empty.
- Pagination: every list the API pages (`?offset&limit` + `total`) has a shared pager (Previous/Next, range label, 5/10/25/50 per page) - datasets, dataset rows, tests, test sets/plans, set entries, plan links, executions, execution runs, standalone runs, and the global runs list. `shared/paged.ts` holds the page state; `shared/pager.component.ts` renders it. The `CatalogStore` still preloads the first 100 of each catalog for counts, name lookups and the overview. Text filters apply to the current page only. The execution page's status tiles summarise the current page (no aggregate endpoint). Runs are enqueue-only - status stays `Pending` until the worker runs; five pages (execution detail, both run detail variants, test detail's standalone runs, the executions panel) poll every 2 s while they're showing a Pending/Running row and stop the instant it settles (`shared/poll.ts`). Nothing else auto-refreshes - the global runs list, Overview, and every catalogue page still just reload on next visit (or the test types page's own manual Refresh button).
- Delete buttons are pre-disabled where the API would 409 (set/plan with executions); other 409s (tests in sets, entries with runs) are shown verbatim.
